# Skill 写作方法

SKILL.md 主体给了准则的结论，本文件给方法与案例。

---

## 一、description 是唯一的战场

DSH 的会话目录**只渲染 `name` + `description`**。`whenToUse` 不参与触发。所以 description 的质量 = skill 的可用性。

### 三个必须回答的问题

1. **它做什么？**（能力边界）
2. **什么时候用？**（触发场景，要具体）
3. **什么情况不用？**（排除条件，防误触发）

### 「pushy」原则

模型天然**欠触发**——倾向于不用 skill 自己硬做。所以 description 要主动推一把。

**弱**：
```
description: 帮助处理 Excel 数据。
```

**强**：
```
description: 帮助处理 Excel 数据——清洗、透视、公式生成、图表制作。
只要用户提到 Excel、xlsx、表格、电子表格、单元格、透视表，或上传了
任何表格类文件，即使没有明说"帮我处理"，也必须使用本 skill。
```

差别在于：后者**主动列举了用户真会说的词**。

### 触发词的来源

不要凭空想。去翻真实对话：

- 用户自己的说法（"润色"而非"文本优化"）
- 口语与书面两种说法（"整理成 Word" / "导出为 docx"）
- 常见缩写和错别字（"xlsx"、"excel表"、"Excle"）
- 邻近概念的反面（用于负例设计）

### 边界怎么写

边界不是"我不做什么"的空话，而是**具体的排除条件**：

```
不适用于：纯粹的语法检查（用 X）、代码格式化（用 Y）、
以及只需要读取 PDF 内容的简单请求。
```

### 长度控制

上限 **400 字符**（本机红线）。DSH 运行时的截断值是 `catalogDescriptionMaxLength`，默认 500，可配；
本机自己收到 400，因为描述都是中文，中文 1 字约 1 token，目录是持久消息、每次会话都在付这笔钱。
超了尾部会被截断，**写在后面的触发词等于不存在**。

所以：**把最重要的触发场景放前面**。

## 二、正文：流程，不是百科

### 核心原则：写判断依据，不写死规则

**差**：
```
禁止使用 ** 加粗，禁止使用 | 表格，禁止使用 # 标题。
```

**好**：
```
如果输出会被直接插入 Word，就要避免一切 Markdown 语法——
`**`、`|`、`#`、`-` 列表都会以原样出现在文档里。判断依据是：
这份内容的终点是不是一个非 Markdown 的文档。
```

后者能泛化到作者没列举的语法上。**这是好 skill 和死板 skill 的分水岭。**

### 解释为什么，不要堆 MUST

写 `ALWAYS`/`NEVER` 是黄旗。停下来问：能不能说清**原因**，让模型自己判断？

模型有推理能力。给了原因，它能在你没预见到的情况下做出正确选择；只给命令，它一遇到边界情况就卡住或照搬。

### 骨架

```markdown
# <它是什么>（一句话）

## 何时用 / 不用
## 核心概念或铁律     ← 领域工具才有
## 工作流程           ← 分步骤，写清"看到什么就怎么判断"
## 输出格式           ← 固定产出才有
## 注意事项 / 常见错误
## 资源导航           ← 何时读 scripts / references
```

按需增删。**不要为了齐全而凑章节。**

### 正文 vs references 的分界

| 放正文 | 放 references |
|---|---|
| 每次都会用到的流程 | 偶尔才查的规格细节 |
| 判断准则 | 完整字段表、枚举清单 |
| 常见错误 | 长案例集 |
| 资源指针 | 背后的原理推导 |

**强烈建议**（创建与调试 skill 时）：正文超过 **200 行** 就应考虑外置；**超过 360 行应当处理**，把细节移入 `references/`。DSH 不检查行数，超出不报错、也不影响加载，但上下文成本会明显偏高。

### 正文 vs scripts 的分界

**同一个逻辑如果每次都要重写一遍，就该固化成脚本。**

典型信号：在多次运行里，模型都独立地写了一遍类似的辅助代码。这不是模型的懒惰，是 skill 缺了东西。

放到 `scripts/` 的好处：
- 不占上下文（脚本不进 prompt，只有调用和输出进）
- 结果一致（不依赖模型每次重新推导）
- 可测试

## 三、领域工具类 skill 的额外要点

如果 skill 封装的是一个已有系统（CLI、库、API）：

1. **先讲它是什么、为什么存在**，再讲怎么用
2. **给最小可运行示例**——一条能直接跑通的命令胜过三段说明
3. **说清失败怎么办**——超时、报错、环境缺失时的处置，特别是"什么时候该停下来问用户"而不是硬试
4. **不要复述工具自带的 `--help`**——那是冗余

---

## 四、常见反模式

| 反模式 | 症状 | 修法 |
|---|---|---|
| 百科式罗列 | 正文很长但模型不知道从哪下手 | 改成流程：先做什么、怎么判断 |
| 死规则 | 大量 ALWAYS/NEVER，边界情况就失效 | 改成判断依据 |
| 触发词藏在后面 | description 前 200 字没有场景 | 把触发场景提前 |
| 把显然的事写成步骤 | "先读取文件，然后分析内容" | 删掉，模型本来就会 |
| 缺少停止条件 | 遇到错误无限重试 | 写清"试 N 次后停下来汇报" |
| 过期信息 | 版本号、路径、API 名过时 | 版本号交给运行时打印，别写死在 skill 里 |
| 复制别的 skill | 与竞争 skill 大段重复 | 合并或明确分工 |

## 五、修改现有 skill 的纪律

1. **先读全文再动手**——不要凭印象改
2. **先跑 `audit.py`**——拿到客观问题清单，避免只改自己注意到的
3. **一次改一个变量**——同时改 description 和正文，触发率变化无法归因
4. **不要改 `name`**——会破坏既有引用；目录名和 name 都应保持
5. **改完重跑体检**——确认没引入新问题
6. **热重载是立刻生效的**——改完 frontmatter 下一个模型步骤就可见，不需要重启

## 六、`disable-model-invocation` 的取舍

判断表：

| 问题 | 是 → |
|---|---|
| 这是硬性约束/安全规则，模型绝不能忽略吗？ | 考虑用户专属 |
| 模型自动触发会造成实质损害吗？ | 考虑用户专属 |
| 只是"希望模型用得好一点"？ | 保持常规，改 description |
| 用户会忘记敲 `/name` 吗？ | 保持常规 |

**默认应该是常规可触发。** 用户专属是重武器，只在"必须人工把关"时用。

典型合适的场景：只读目录约束、发布/删除类危险操作的前置检查、涉及凭据的流程。

## 七、第三方技能：装进来之前要读一遍

随程序包分发的技能（pip / npm 包在自己目录里塞一份 SKILL.md，装包时由安装脚本
复制进技能目录）和用户自己写的技能有本质区别：**它带着作者自己的立场**。

关键在于，这类技能通常是写给**没有内置工具的通用 agent** 的。在那种环境下，
"优先用我""不要用别的工具"是合理建议。但 DSH 已经有内置工具了，这个前提不成立，
而**模型分不清"厂商自我定位"和"用户策略"**——两者进入指令空间后长得一模一样。

### 四类要检查的问题

| 类型 | 为什么要看 | 真实例子（`searchts`） |
|---|---|---|
| **排斥性声明** | 正文若说"我是首选""不要用别的工具"，会和你的实际策略打架 | *"they are the preferred path. Do not reach for raw `curl`, `r.jina.ai`, or other tools…"*、*"use it before falling back to a built-in fetch"* |
| **死字段** | 上游按别的 harness 的写法写 frontmatter，DSH 静默忽略 | `triggers:` 字段，11 行关键词表**一个字都不生效** |
| **超长 description** | 上游不知道 DSH 会截断目录描述（默认 500 字符，本机红线 400） | 原 description 1775 字符，截断点正好切掉整段 `NOT for` 边界 |
| **平台假设** | 路径、工具名、约定可能来自别的平台 | `Use /tmp/` 在 Windows 上不存在 |

`audit.py` 的 **W7** 自动抓第一类。判据是：**同一处散文里既有"优先/禁止"措辞、
又点了工具名**（扫描时跳过代码块与表格行，避免把"引用这类说法"误判成"主张这类说法"）。
其余三类由 W6（死字段）、W1（description 长度）和人工阅读发现。

### 处理原则：先认清"更新"有多彻底

装包时**不是"覆盖某个文件"，而是把整个技能目录删掉重建**。以 `searchts` 为例
（`searchts/cli.py:520-529`）：

```python
elif os.path.exists(target):
    shutil.rmtree(target)          # ← 整个目录被删
os.makedirs(target, exist_ok=True)
```

所以被冲掉的**不只是 SKILL.md**：`references/` 里的改动、以及你放进那个目录的
**任何本地文件**，全部一起消失。由此得出一条硬规矩：

> **对第三方技能，所有本地资产都必须放在技能目录之外。**

### 三个层次的做法

| 放哪 | 放什么 | 特点 |
|---|---|---|
| `$DSH_HOME/AGENTS.md` | **你要生效的策略**，并点名覆盖上游主张（"某技能自称 the preferred path，在 DSH 上前提不成立，以本规则为准"） | 常驻、改不动、优先级高。**模型遇到冲突时需要一句明确的裁决**，否则只能自己猜 |
| **改技能正文**，在顶部加一段必读说明 | 来源（哪个包、怎么装进来的）、已改过什么、更新的代价、建议不要轻易更新 | 模型**加载技能时**就读到，正好赶在它准备提议更新之前。代价：**这段说明会被它警告的那次更新抹掉**，是自我毁灭的 |
| **技能目录之外**，如 `~/.dsh/<skill>-local-patch.md` | 补丁说明：为什么需要、何时重打、**可执行的自检脚本**、每处改动的精确替换内容 | 唯一能撑过更新的，是前两层的兜底 |

三层各管一段：**AGENTS.md** 管"冲突时听谁的"，**技能内必读说明**管"提议更新时说出代价"，
**补丁说明**管"更新之后怎么复原"。只做一层都不够。

> 补丁说明**不要**放在技能根目录下 —— 平铺的 `<root>/<name>.md` 会被 DSH 当成一个
> 技能来发现，凭空多出一个幽灵条目。

### 顺带：这类技能往往也需要本地修正

因为它们不是为 DSH 写的，常见的还有：description 超长、把关键信息写进死字段、
引用别的平台的路径与工具名。这些都要在装进来之后按本 skill 的模式 B 处理，
并且同样记进补丁说明——否则下次更新全部重来。
