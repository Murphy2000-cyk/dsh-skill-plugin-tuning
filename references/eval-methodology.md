# 触发准确率评估方法

SKILL.md 主体给了流程，本文件给方法论——怎么设计用例、怎么读结果、怎么迭代。

---

## 一、为什么需要它

skill 最常见的失效不是"写得不好"，而是"**根本没被用上**"。

这个问题平时无法自测：
- 你觉得 description 很清楚，但模型不这么认为
- 你无法观察"这次模型到底有没有查 skill"
- 靠感觉调 description，等于盲改

DSH 的 session 日志完整记录了每次工具调用，所以**这件事是可以客观测量的**。

---

## 二、测量原理

```
dsh --profile headless "<查询>"     ← 一次性任务，无 GUI、无端口，退出码 0/1
        ↓
读该次运行的 session 日志             ← $DSH_HOME/sessions/<cwd-key>/<uuid>/session*.jsonl.zstd
        ↓
筛 type=="tool/call" 且 data.name=="skill"
        ↓
解析 data.arguments → {"name": "<skill名>"}
        ↓
这就是本次的触发决策
```

**关键优势：不依赖模型自述。** 这是真实发生的工具调用记录，不是模型的自我报告。

**日志是 zstd 压缩的 JSONL**，需要 `zstandard` 库。`tool/call` 事件的结构：

```json
{"type":"tool/call","seq":18,"time":1787196245999,
 "data":{"turn":1,"step":1,"callId":"call_00_...","name":"skill",
         "arguments":"{\"name\":\"text-polish\"}"}}
```

## 三、设计用例集

### 规模

**应触发 8-10 条 + 不应触发 8-10 条**，共 16-20 条。

触发有随机性，所以每条建议**重复 3 次**取触发率。20 条 × 3 次 ≈ 40-60 分钟。先跑 1 次筛掉明显问题，再对关键用例跑 3 次。

### 应触发的用例（正例）

要覆盖**同一意图的不同说法**：

| 类型 | 例子（以文档润色 skill 为例） |
|---|---|
| 直接点名 | "用润色功能处理一下这个" |
| 口语说法 | "这段话读着太随便了，帮我改成正式点的" |
| 不点名但明显需要 | "这份稿子要发给甲方，你看看措辞合适吗" |
| 专业术语 | "把这段转成书面语" |
| 竞争情形 | "帮我把这份 Markdown 整理成 Word 文档"（与"格式转换"类 skill 竞争，本 skill 应赢） |
| 短查询 | "润色：这个方案还行，但有点问题" |

### 不应触发的用例（负例）—— 最重要

**负例的质量决定评估的价值。**

**关键原则：选"近似误触发"，不要选显而易见的无关请求。**

❌ **无效负例**："写个斐波那契函数"——对文档 skill 毫无测试价值，任何 description 都能通过。

✅ **有效负例**：
- **共享关键词但意图不同**："帮我读一下这个 PDF 说了什么"（涉及文档，但只需读取）
- **只有一半相关**："检查一下这份文档有没有错别字"（可能该用别的 skill）
- **上下文中提到但不需要**："我们上次润色的那个文档放哪了"（是查询，不是润色请求）
- **相邻领域**："把这段代码格式化一下"（也是"格式化"，但对象是代码）

### 真实性要求

用例必须像**真人会打的字**：

- 带文件名、路径：`F:/工作/报告初稿.docx`
- 带背景：`我老板让我把这份 Q4 数据整理一下`
- 口语、缩写、错别字
- 长短混合：有的很长带一堆细节，有的就三五个字

抽象的"格式化数据"、"处理文档"测不出任何东西。

## 四、解读结果

| 现象 | 诊断 | 处方 |
|---|---|---|
| 应触发命中率 **低** | **欠触发** —— 最常见的病 | description 补用户真会说的触发词和场景 |
| 误触发率 **高** | 边界不清，或与竞争 skill 撞词 | description 加"不适用"段；跑 `audit.py` 看触发词重叠报告 |
| **两者都低** | description 与正文主题不一致 | 重新对齐：description 承诺的事，正文要真的讲 |
| 命中率 **100%** 且误触发 0% | 用例太简单，没有区分度 | 加难度：更多近似误触发、更口语化的正例 |
| 结果**不稳定**（重跑变化大） | 触发本身随机，或用例太模糊 | 提高 `--repeat`；把模糊用例改具体 |

### 阈值参考

- 应触发命中率 **≥ 80%** 算健康
- 误触发率 **≤ 20%** 算健康
- 低于此值就该改 description

## 五、迭代纪律

**每次只改一个变量。**

同时改 description 和正文，触发率变化了也无法归因——你不知道是哪个改动起作用。

推荐循环：

```
1. 基线评估（cases 固定）
2. 只改 description
3. 重跑（同一 cases）
4. 对比命中率/误触发率
5. 有效 → 保留；无效 → 回退，换一个思路
6. 重复
```

**保留 cases 文件**，它是唯一能证明"改动有效"的东西。改了 cases 就没法对比了。

## 六、成本与工程注意

### 探测超时：只测触发，不跑完任务

**关键设计**：评估只关心"skill 有没有被加载"，而**加载发生在任务最开始**。之后模型会真的去执行整个工作流——创建工作流可能耗时数分钟——但那对判定毫无价值。

所以脚本在 `--probe` 秒后**主动掐断进程**，解析已增量落盘的日志。这把单条用例从数分钟压到 1-2 分钟。

- 默认 `--probe 120`；模型较慢时调大
- 若日志里已有 skill 调用 → 判定为触发
- 若掐断时仍无 → 判定为未触发
- 结果里会标注哪些运行被掐断（不影响判定有效性）

**诊断提示**：如果大量用例都"未触发"且都被掐断，先调大 `--probe` 排除"加载发生得太晚"这个可能，再怀疑 description。

### 其他

- **每条查询是一次完整 agent 运行**，有 token 消耗
- **跑之前告知用户**，并在后台运行（`run_in_background`）
- **不要用评估替代真实使用**——它是抽样，不是全覆盖
- **评估结果不代替人工判断**：主观产出（文风、设计质量）不适合用触发率衡量

### 环境前置

- `dsh` 在 PATH 中
- `zstandard` 已安装
- `headless` profile 存在（`eval_trigger.py` 会自动创建）
- 会话目录可读

跑 `python scripts/eval_trigger.py --check` 一次性验证全部前置条件。

## 七、这个方法的边界

**能测**：skill 是否被加载（触发决策）。

**不能测**：
- 加载后模型**有没有正确执行**正文的指令 —— 这需要读运行轨迹做人工评审
- 产出质量 —— 需要人工看输出
- 多轮对话中的触发 —— headless 是单轮的

**如果要测"执行是否正确"**：给每个用例加 `expected_output` 描述，跑完后把产出（或轨迹）交给人工或独立评审 agent 打分。本 skill 不自动化这一步——主观判断不该被指标替代。

---

## 八、评估之外的两个免费信号

即使不跑完整评估，也能从真实会话里获得信息：

1. **翻自己的历史 session 日志**，看 `skill` 工具调用的分布：
   - 某个 skill **从来没被调用过** → 要么 description 有问题，要么它根本不需要存在
   - 某个 skill **在无关任务里被调用** → 误触发

2. **看模型有没有"绕过" skill**：如果它在 reasoning 里明确说"这不需要 skill"，那是个强信号——说明该 skill 的 description 让它觉得"不适用"。
