# skill 侧细则

本文件是 skill 这一支的完整规则：硬约束、触发机制、创建与修改流程、description 写法、验证、触发评估、常见错误。
**总框架、两侧分流、两套校核标准、共同纪律在 `SKILL.md`**，先读那份再进这里。插件包不走这条路，看 `references/plugins.md`。

## 一、DSH 的硬约束与触发机制

### 6 条铁律

违反会直接失效。完整规格见 `references/dsh-spec.md`。

| # | 约束 | 违反后果 |
|---|---|---|
| 1 | `name` 必须匹配 `^[a-z0-9]+(-[a-z0-9]+)*$`（**全小写**，只能 ASCII 字母数字和连字符） | **整个 skill 被静默丢弃**，不报错 |
| 2 | `description` 必填、非空 | 同上 |
| 3 | 发现深度**只有一层**：`<root>/<name>/SKILL.md` 或平铺 `<root>/<name>.md` | 嵌套目录里的 skill 找不到 |
| 4 | 会话目录里**只渲染 `name` + `description`** | `whenToUse` 对触发**毫无作用** |
| 5 | description 超过 **400 字符**（本机红线；DSH 运行时默认截断 500，可配） | 超长部分模型看不到 |
| 6 | 目录是**持久消息**，正文是**工具结果** | 两者都常驻消耗 token |

**第 4、5 条最容易踩**：`whenToUse` 合法但不参与触发；description 超 400 的部分彻底消失。**把最重要的触发场景放最前面。**
**为什么命名是全小写**：DSH 用它做跨来源合并时的唯一键。目录名只用于发现，skill 身份由 `name` 决定。

### 触发是怎么发生的

有**两条独立路径**，走两个界面、受两个不同开关控制：

| 路径 | 谁发起 | 依据什么 | 关闭它的开关 |
|---|---|---|---|
| **模型自动** | 模型判断 | 会话目录里的 **description** | `disable-model-invocation: true` |
| **用户显式** | 用户敲 `/name` | `/` 菜单里的 **skill 名** | `user-invocable: false` |

同一份 frontmatter 服务两个表面。**改 description 只影响第一条路径**；第二条路径看的是名字。

模型看到的目录形态：

```
<available_skills>
- `name`: <description，超过 400 字符会被截掉尾部>
</available_skills>
```

末尾指令是："If the user **names a skill**, or the task **clearly matches a skill's description**, call the `skill` tool"。

所以模型自动触发只有两种情形：**用户说出了 skill 名**，或**模型读了 description 后判断任务匹配**。

### 查不清时的顺序

先看会话目录里模型**实际看到**的 description，再读 SKILL.md 正文，再翻 `references/`，最后才读 DSH 源码。
前一步能回答的不要跳步——目录里没有的东西模型就是看不见，这比正文里写了什么更优先。

### 没有触发词机制

**DSH 没有关键词表、没有正则、没有匹配打分。** 触发是**模型读文本后的语义判断**，不是程序匹配。

所以「触发词」**不是机制，是写作技巧**——往 description 里写用户真会说的原话，只是给模型的语义判断多提供一点线索。

⚠️ **由此产生一个高频误解**：自己加 `triggers:` 之类的字段来"注册关键词"。DSH 不认，静默忽略。真实案例：某 skill 写了 592 字符的 `triggers:` 关键词表，**一个字都没生效**。

### 只认这 6 个字段

```
name · description · whenToUse · metadata · disable-model-invocation · user-invocable
```

**其余字段一律静默忽略**——不报错、不警告，就当不存在。这类"死字段"（`triggers`、`trigger`、`version`、`author`…）的危害是**让人误以为生效了，从而没把信息放到真正起作用的地方**。`audit.py` 的 W6 检查会抓出来。

### 两个调用开关的默认值

`disable-model-invocation` 与 `user-invocable` 都是**可选字段，省略即允许**——模型可自动触发，用户也可 `/name` 调用。**绝大多数 skill 不该设它们。**

⚠️ **值写错会丢弃整个 skill**（不是退回默认值）。只接受 YAML 布尔与不区分大小写的 `true/false`、`yes/no`、`on/off`、`1/0`。写 `是` 或 `true-ish` 会让技能直接消失。

## 二、三种模式

先判断用户处于哪一种，再进入对应流程。拿不准就问一句。

| 用户意图 | 模式 |
|---|---|
| "帮我做一个 X 的 skill" | **A 创建**（第三节） |
| "这个 skill 改一下 / 优化一下 / 重构" | **B 修改**（第四节） |
| "检查一下这些 skill" / "为什么没触发" / "skill 没生效" | **C 体检 + 排查**（第五节） |

**触发评估（第七节）不属于这三种模式**——它是改完之后的附加动作，用户同意才做。框架里把它列成第四条流程，指的是这个动作，不是第四种模式。

## 三、模式 A：创建

**先落一个能触发的最小版本，再补细节**：写完 frontmatter 加三五句正文就装上，确认它出现在目录里，然后才加流程、边界、references。反过来（先写三百行再验证）一旦没加载，你分不清是哪一半出的问题。也不要用"description 五个变体"或"模拟触发脚本"替代真实加载。

### A1. 先问清楚四件事

不要一上来就写文件。这四个问题的答案直接决定 skill 的形态：

1. **它让 agent 能做什么？**（一句话）
2. **什么时候该触发？**（用户会怎么说出这个需求——要具体到措辞和场景）
3. **产出是什么形态？**（改文件 / 给答案 / 跑脚本 / 生成文档）
4. **要不要建测试用例？** 产出客观可验证的（文件转换、数据提取、固定流程）值得建；主观的（文风、设计）不必勉强。

同时主动追问边界：**什么时候不该用它？** 边界比能力更能防止误触发。

### A2. 判断该不该做成 skill

这是最容易被跳过、也最值得花时间的一步。DSH 的触发机制有个关键特性：**模型只对"自己搞不定的复杂多步任务"才去查 skill**。简单单步请求（"读一下这个 PDF"）即使 description 完美匹配也不会触发，因为模型用基本工具就能做完。

所以：如果一个任务的步骤对模型是显然的，写成 skill 是浪费。**值得做成 skill 的是：领域知识密集、步骤非显然、或者需要固化特定输出格式的任务。**

### A3. 决定结构

```
<name>/
├── SKILL.md          必需。frontmatter + 指令正文
├── scripts/          确定性、可重复的操作用代码固化
├── references/       按需加载的长文档
└── assets/           输出用的模板、图标、字体
```

**判断规则**（这是渐进式披露的实操）：

- 正文 **<200 行** 能说清 → 只有 SKILL.md，够了
- 正文要 **>200 行** → 把细节移到 `references/`，正文只留流程和指针
- 有**每次都要重写一遍**的确定性逻辑 → 写进 `scripts/`（省 token，且保证一致性）
- 有**输出模板** → 放 `assets/`

**强烈建议：正文不超过 360 行。** 这是创建与调试 skill 时的强烈建议。它**不是硬性限制**（DSH 不检查行数，超了不报错、不影响加载），但超出会明显推高上下文成本，因为正文每次触发都会进上下文。超过就把细节外置到 `references/`。

### A4. 写 description（这是最重要的一步）

`description` 是**模型自动触发的唯一依据**（另一条路径是用户敲名字，见第一节）。要点：

- **同时包含"做什么"和"什么时候用"**
- **要"pushy"**：模型天然倾向于欠触发。所以不要只写"如何做 X"，要补一句"只要用户提到 A、B、C，即使没说 X 也要用本 skill"
- **列举真实触发场景**：用户真会说的原话、专业术语、口语说法都要覆盖（这是写作技巧，不是注册关键词）
- **写清边界**：明确"不适用"的情形，能显著减少误触发
- **越短越好，但边界是语义**：目录每轮都在付费（中文 1 字约 1 token），400 是上限不是目标、`audit.py` 的 40 是下限也不是目标。先删同义例句和修饰，删到"每类真实请求都还匹配得上"就停手
- **不该省的两处**：引号里的触发词（删光触发 W2），以及"这个 skill 能做什么"那半句——它是用户不点名时唯一的匹配依据

反面例子 `description: 帮用户处理文档。`；正面例子见本文件 frontmatter。

### A5. 写正文

常用骨架（何时用 / 不同、铁律、工作流程、输出格式、常见错误、资源导航），按需增删。
完整骨架与"正文 vs references/scripts 的分界"见 `references/authoring.md` 第二节。

### A6. 交付前检查

**不跑完这四步不算完成：**

1. **静态体检**：`python scripts/audit.py --skill <name>` —— 必须 0 错误
2. **确认可见**：走一遍第六节的三步确认（尤其 `/` 菜单，**记得刷新页面**）
3. **（可选）触发评估**：用户同意后跑第七节
4. **保持原名**：改现有 skill 时**不要**改 `name`，否则破坏既有引用

## 四、模式 B：修改

先诊断，再动手。**不要没看清单就重写。**

1. **读原文**：`read` 完整的 SKILL.md
2. **跑体检**：`python scripts/audit.py --skill <name>`，拿到问题清单
3. **定位问题类型**：

| 症状 | 病因 | 处方 |
|---|---|---|
| 不触发 | description 缺触发场景 / 太笼统 | 重写 description（A4 要点） |
| 误触发 | 边界不清 / 与别的 skill 触发词重叠 | 加"不适用"段；看 `audit.py` 的重叠报告 |
| 触发但用得不对 | 正文是知识罗列，缺流程 | 改成步骤化流程，说清判断依据 |
| 正文太长 | 细节没外置 | 移入 `references/`，正文留指针 |
| 每次都重写同样的代码 | 缺 `scripts/` | 固化成脚本 |
| 模型不遵守硬规则 | 该用用户专属调用 | 考虑 `disable-model-invocation: true`（见下） |
| 信息写在死字段里 | 被静默忽略 | 移进 `description` 或正文 |

4. **改完再跑一次体检**，并确认仍然可见（第六节）
5. **热重载**：改 frontmatter 会立即刷新**模型侧**目录，不需要重启；但**用户侧 `/` 菜单需要刷新页面**

### 关于「用户专属 skill」

`disable-model-invocation: true` 让 skill **模型看不到、无法自动触发**，只能由用户手敲 `/<name>` 注入。适用于硬性约束、安全规则、必须由人显式启用的流程（例如"某目录只读禁写"）。
**代价**：模型不会主动用它，你得记得敲。只对"必须人工把关"的规则用，**默认应该是常规可触发**。

## 五、模式 C：体检

```bash
python scripts/audit.py                    # 体检全部 skill
python scripts/audit.py --skill <name>     # 体检单个
python scripts/audit.py --json             # 机器可读输出
```

`audit.py` 覆盖 14 项，编码即报告里每行的前缀：

| 编码 | 查什么 | 级别 |
|---|---|---|
| E1 / E2 | SKILL.md 读不到 / frontmatter 缺失或解析失败 | 错误 |
| E3 | `name` 缺失或非法（必须全小写 kebab-case） | 错误 |
| E4 | `description` 缺失 | 错误 |
| W1 | description 长度（超 400 会被截断；过短几乎不可能触发） | 警告 |
| W2 | description 没写触发词，或只写"做什么"不写"何时用" | 警告 |
| W3 | 用了 `whenToUse`（不进入会话目录，对触发无作用） | 警告 |
| W4 | 正文行数超过建议值（本机红线 360） | 警告 |
| W5 | 跨 skill 触发词重叠（只有扫描整批时才出现） | 警告 |
| W6 | 未知 frontmatter 字段（死字段） | 警告 |
| W7 | 正文存在排斥性声明 | 警告 |
| I0 | `name` 与目录名不一致（合法，仅提示） | 提示 |
| I1 | 正文长但没有 `references/` 目录 | 提示 |
| I2 | 两个调用开关的设置提示 | 提示 |

报告尾部还会给目录常驻 token 与正文 token 的粗估——那不是判据，是账单。

插件包的体检是另一支：`scripts/audit-plugin.mjs --path <目录>`，覆盖范围与专项清单见 `references/plugins.md`。

拿到报告后，按"错误 → 警告 → 建议"的顺序处理，并把结论讲给用户听，不要只丢一串检查项。

### 脚本查不到的那一维

名词与数值一致性两个脚本都不查，但它对 skill 和插件都适用，判据与做法写在 SKILL.md 的「共同纪律」里。

### 第三方技能：自动检查之外还要读一遍

随程序包分发的技能自带它作者的立场，而且通常写给**没有内置工具的通用 agent**，容易带来排斥性声明、死字段、超长 description、平台假设四类问题（`audit.py` 的 W7 只抓第一类，四类的实例与处理办法见 `references/authoring.md`）。
**关键处理原则**：不要改上游文案（更新会冲掉）。要把生效策略写进 `$DSH_HOME/AGENTS.md` 并**点名覆盖**——模型遇到冲突时需要一句明确的裁决。

## 六、验证 skill 已生效

创建或修改后**必须确认它真的被加载了**——这是最容易踩空的一步。

### 三步确认

| 步 | 怎么做 | 通过标准 |
|---|---|---|
| 1. 静态合规 | `audit.py --skill <name>` | 0 错误 |
| 2. 模型目录可见 | 看当前会话的技能目录里有没有它 | 出现，且 description 未被截断 |
| 3. 用户菜单可见 | Web UI 输入 `/` + 名字前几个字母 | 出现在候选中 |

`/` 菜单的匹配是**不区分大小写的有序子序列**，**前缀命中排最前**。本技能名以 `dsh-` 开头，所以输入 `/dsh` 时它必然排在候选前列——**如果不在，就是没被加载**。

### 不在列表里？按这个顺序排查（命中概率从高到低）

| # | 症状 | 病因 | 处理 |
|---|---|---|---|
| 1 | 刚创建，模型目录有、`/` 菜单没有 | **客户端缓存** | **按 F5 刷新页面** |
| 2 | 两边都没有 | `name` 非法（大写/中文）→ 整个 skill 被丢弃 | 改全小写 kebab-case |
| 3 | 两边都没有 | 文件层级不对 | 必须 `<root>/<name>/SKILL.md` |
| 4 | 两边都没有 | frontmatter 解析失败（缺 `---`、YAML 错） | `audit.py` 会报 E2 |
| 5 | 只有部分出现 | 同名冲突，被 rank 更高的层遮蔽 | 检查项目根 `.dsh/skills`、`.agents/skills` |
| 6 | 改名后消失 | 改了 `name` 字段 | 恢复原名（或同步改目录名与所有引用） |
| 7 | 一直不出现 | 根目录 watcher 没生效 | 重启 dsh |

**第 1 条最反直觉，也最常见**：模型侧技能目录**热重载**（改完立刻生效），但 **Web UI 的 `/` 菜单不会自动刷新**。看到菜单里没有就以为写错了，会去改本来正确的 frontmatter。

### 什么不算验证

这些经常被当成"验过了"，其实都不是：

- 文件在目录里 ≠ 会被加载（`audit.py` 只证明格式对）
- 出现在模型目录 ≠ 会被触发（要跑第七节）
- 触发过一次 ≠ 每次都对（那是抽样，不是保证）；自己看了一遍 ≠ 用户 `/` 菜单里有

**报结论时把边界说出来**：验到了哪一步、哪一步没验、为什么。

## 七、触发准确率评估

本 skill 最有价值也最耗时的能力。它回答一个平时很难自测的问题：**这个 skill 到底会不会被触发？**

原理是 HEADLESS 跑一轮、再读 session 日志看有没有 `tool/call` 到 `skill`——不依赖模型自述。
完整原理、日志字段与边界见 `references/eval-methodology.md` 第一、二、七节。

### 用法

```bash
# 1. 生成测试用例模板（20 条：10 条应触发 + 10 条不应触发）
python scripts/eval_trigger.py --skill <name> --gen

# 2. 人工审阅、修改 cases.json，然后跑
python scripts/eval_trigger.py --skill <name> --cases cases.json

# 3. 每条重复 3 次取触发率；调小探测超时加速
python scripts/eval_trigger.py --skill <name> --cases cases.json --repeat 3 --probe 60

# 4. 只看结果
python scripts/eval_trigger.py --skill <name> --cases cases.json --json
```

**关于 `--probe`**：只关心"skill 有没有被加载"，而加载发生在任务最开始。之后模型会真的去执行整个工作流（可能数分钟），对判定毫无价值。所以脚本在 `--probe` 秒后主动掐断，解析已落盘的日志——这把单条用例从数分钟压到 1-2 分钟。默认 120 秒。

### 设计用例与读结果

**应触发 8-10 条**（正式、口语、不点名但明显需要），**不应触发 8-10 条**（最有价值的是"近似误触发"）。命中率低是**欠触发**，误触发高是**边界不清**，**每次只改一个变量**。完整用例设计与阈值见 `references/eval-methodology.md` 第三、四节。
**不许为了让数字好看去改 cases.json**——那等于改尺子再说自己长高了，这次评估作废。

### 局限

headless 是**单轮**的，测不出多轮对话中的触发；也测不出"加载后模型有没有正确执行正文指令"——那需要人工看轨迹。

## 八、写作准则

1. **解释"为什么"，而不是堆大写 MUST。** 模型有推理能力，说明原因它才能在没预见到的情况下泛化。如果你在写 `ALWAYS`/`NEVER`，先停下想想能不能改成解释。
2. **给判断依据，不给死规则。** 写"如果输出要被直接插入 Word，就避免 Markdown 语法"，比写"禁止使用 `**`"更好——前者能泛化到 `|`、`#` 等没列举的情况。
3. **流程化而非罗列化。** 领域知识要落到"先做什么、看到什么就怎么判断"。
4. **说清边界。** 什么时候不用、什么情况下停手。
5. **例子胜于形容词。** 一个正例一个反例，比"要准确"有用得多。
6. **不要把模型本来就会的事写成步骤，也不要写没用的字。** 正文每个字每次触发都要花钱。

## 九、常见错误

| 错误 | 后果 | 修法 |
|---|---|---|
| `name` 用了大写或中文 | skill 被静默丢弃 | 全小写 kebab-case |
| 把触发场景写进 `whenToUse`、或写了 DSH 不认的字段（`triggers`、`version`、`author`…） | 被静默忽略，等于白写 | 只用那 6 个合法字段，触发信息写进 `description` |
| 以为有"触发词注册"机制 | 关键词表不生效；真正该写的 description 反而没写 | 触发信息一律写进 description |
| description 只写"做什么"不写"何时用" | 不触发 | 补场景 |
| description 超 400 字符，或调试期反复重写它 | 尾部截断；每次重写都追加一整份目录，推高上下文 | 一次想清楚，精简到 400 内；改正文更安全 |
| description 用纯标量却含 `冒号+空格` | YAML 当成嵌套映射，**frontmatter 解析失败，整个 skill 掉**（E2/E3/E4） | 改成 `Triggers "..."`，或改用 `description: >` 折叠块 |
| 正文塞了 500 行领域知识 | 每次触发烧大量 token | 移到 `references/` |
| 嵌套目录放 SKILL.md | 找不到 | 必须放在根下一层 |
| 误用 `user-invocable: false` / `disable-model-invocation: true` | 用户敲不到，或模型完全看不到它 | 除非"必须人工把关"，否则省略这两个字段 |
| 改现有 skill 时改了 `name` 却不同步目录名与引用 | 既有引用断裂 | 保持原名，或一次性改全 |
| 改完不验证是否可见 | 可能根本没被加载 | 走第六节三步确认 |
| 正文写死绝对路径引用自己的脚本 | 技能来自远程或换机器时必然失效 | 用相对路径，按 Agent 给的资源基底解析 |
| 写了非法布尔值（`是`、`true-ish`） | **整个 skill 被丢弃** | 只用合法写法，见第一节 |
| 改了正文就以为进行中的会话会更新 | 它手上仍是旧正文 | 让它重新加载，或新开会话 |
| 第三方技能自称"首选"、要求别用内置工具 | 模型分不清厂商定位与你的策略，可能压过你真正的路由 | 在 `$DSH_HOME/AGENTS.md` 写明路由规则覆盖它（`audit.py` 的 W7 会抓） |

## 十、能力与边界（skill 侧）

**能做到的**（可执行、可复现）：

- 结构合规：14 项判据，`audit.py` 一条命令出结论
- description 质量：长度、触发词、边界、"做什么"那半句在不在
- **触发准确率可以量化**：`eval_trigger.py` 跑 headless、读 session 日志里的 `tool/call`，不依赖模型自述
- 批量体检与目录描述精简：一次扫全部 skill，报重叠与体积

**做不到的**（别把"审计通过"说成"调好了"）：

- **加载后模型有没有正确执行正文指令**——要人看运行轨迹，脚本测不出
- **产出质量**——文风、设计、判断是否恰当，只能人评
- **多轮对话中的触发**——headless 是单轮的
- 触发率是抽样，不是保证；一次 100% 不等于以后都对

**待补**：

- 把"执行是否正确"做成可复用的评审清单（现在只有 `references/eval-methodology.md` 第七节的思路）。
- **成对基线评估**（同一用例跑带 skill 与不带两遍，比产出差异，回答"加了 skill 有没有让结果变好"）。**已决定暂不做**，不是忘了：本机跑一对子代理 ≈ 两次完整任务，成本不低，而当前几个 skill 要么明显有用、要么根本不该存在，不需要靠效果对比来决策。真遇到"新版本到底有没有更好"这类问题时再做——那时可以借用插件侧已有的 smoke + 契约脚本当固定基线，比纯靠人看更省。
