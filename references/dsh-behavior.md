# DSH 运行期行为特性

`dsh-spec.md` 讲的是**静态硬规格**（字段、rank、发现规则），本文件讲**运行期行为**：DSH 在技能加载、注入、计费上的实际表现，以及这些表现如何影响 skill 的写法。

全部内容来自官方包文档（`dsh-skill`、`dsh-skill-filesystem`、`dsh-tool-skill`），非推测。

---

## 一、与其他 Agent 框架的定位差异

| 维度 | DSH | 典型其他框架 |
|---|---|---|
| 技能来源 | **可插拔注册表**，支持磁盘、插件内嵌、远程 | 固定扫描本地目录 |
| 调用策略 | **模型与用户两个独立维度** | 模型侧单一 |
| 触发方式 | **纯语义判断**，无关键词机制 | 多为描述匹配，部分有关键词 |
| 发现深度 | **刻意只有一层** | 常见支持嵌套 |
| 热重载 | 监视加免重启 | 需重新加载 |
| 资源基底 | 可为目录、URL 或不透明 | 通常就是本地目录 |
| 打包格式 | **无**，技能即目录 | 常有专有打包格式 |

**推论**：不要照搬其他生态的技能写法。特别是"注册关键词""写绝对路径引用资源""打成包分发"这三件事，在 DSH 上都不成立。

## 二、技能目录的生命周期

### 目录是持久 user 角色消息

模型收到的技能目录是一条**持久的 user 角色消息**（不是 system prompt），在首个请求之前注入。

**影响**：目录的 token 成本随技能数量线性增长，且每个会话都要付。这是"每个技能都该精炼"的根本原因。

### 只渲染名称与描述

目录里只有 `name` 和 `description`，不含 `whenToUse`、来源、提供方元数据。描述被截断到 `catalogDescriptionMaxLength`（默认 500）。

### 变更是全量替换，不是增量

任何成员、描述或可见性变化，都会**追加一整份完整目录**（所有可见技能的摘要）。

**影响**：调试期反复微调 description，每次都在会话历史里追加一份目录。**描述应一次想清楚，不要在生产会话里反复改。**

### 目录可能被整体省略

只有"存在模型可调用技能**且** `skill` 工具可见"时才会注入目录。

**影响**：若把所有技能都设成 `disable-model-invocation: true`，模型**完全不知道技能机制存在**，不会提示用户去用 `/name`。

### 提供方快照不完整时不发送

某个技能来源读取失败时，插件**什么都不发**，并为下一步保留上一份可用视图。

**注意适用范围**：这**只发生在提供方故障时**（文件系统读取错误、远程来源失败等），**不是删除技能的后果**。

**正常删除会发生什么**：目录 digest 变化 → 追加一份不含该技能的新目录 → 模型立刻看不到它。**没有残留。**

**故障时的现象**：会话里那条旧目录消息没有被替换，模型仍看到旧名字。但它若真去加载，会收到"该技能未知或已不可用"的错误。

**调试提示**：模型提到一个已删除的技能时，先怀疑来源读取失败，而不是模型幻觉。

### 工具遮蔽会清空目录

作用域内出现同名工具遮蔽 `skill` 工具时，schema 与指引会**同时**被移除，并追加空目录停用旧名称。

## 三、正文的生命周期

### 加载一次，之后作为历史重发

正文通过 `skill` 工具加载**一次**，成为一条**保留的工具结果**。此后：

- **不会重复读取文件**
- **不会"加载所有匹配的技能"**：只有模型显式调用 `skill`（或用户敲 `/name`）才会加载正文，目录里只有摘要
- 后续**每次 API 请求**都会把完整对话历史发给模型，因此这段正文被**重新发送**，直到压缩把它裁掉

```
提问 → 请求1（无正文）
模型调用 skill → 请求2（有正文）← 读取只发生在这里
模型下一步 → 请求3（历史里仍有正文）← 重发
...
直到压缩裁掉
```

所谓"每步重发"，指的是**作为历史被重新发送**，不是重新加载。

### 正文没有大小上限

官方把"已加载指令正文没有大小上限"列为已知限制。提供方可以返回足以占用大量上下文的正文。

### 正文不做版本化

**仅修改正文不会改变目录 digest，也不会通知模型。** 后续工具调用会读取提供方的当前内容，但**先前那条工具结果仍是历史事实**。

**影响**：修改了技能正文后，**正在运行的会话里模型手上仍是旧正文**，只有它再次调用 `skill` 才会拿到新内容。

**调试提示**：改了正文但当前会话行为没变，别急着判定"技能写错了"，先意识到会话可能还拿着旧版。

### 压缩后可能丢失

正文是普通工具结果，会被上下文压缩裁剪。裁掉之后模型就"不记得"自己加载过什么。

**影响**：关键约束不能只依赖技能正文长期在场。要么短到不易被裁，要么在正文里要求模型复述要点。

## 四、成本模型

| 部分 | 何时计费 | 说明 |
|---|---|---|
| 目录（description） | **每次请求** | 常驻，随技能数量线性增长 |
| 正文 | **加载后的每次请求** | 落在稳定前缀内，按缓存命中计价 |
| 首次加载 | 一次 | 按缓存未命中计价 |

**关键认识：重发的 token 按缓存命中计价，价格远低于未命中。**

DSH 采用上下文缓存，重复的稳定前缀以缓存命中价格计费（官方价格页显示命中与未命中相差约五十倍）。

**所以超长技能的真实代价不是钱，而是上下文窗口占用**：它挤压真正有用的内容，并让压缩更早发生，而压缩又会裁掉技能正文，形成"加载了又被裁掉"的浪费。

**由此得出两条实践规则**：

1. 正文要短，理由主要是**上下文占用**，不是费用
2. 频繁改 frontmatter 会持续追加目录消息，这条的成本比改正文更值得警惕

## 五、用户显式调用路径

### `/name` 是 `disable-model-invocation` 的唯一入口

这类技能**不出现在模型目录中，也无法被模型加载**，只能由用户敲 `/name` 注入。

### 注入位置在该步骤所有注入之后

`/name` 的内容作为 **user 角色的指令上下文**注入，**追加在该步骤所有其他注入之后**（设计意图：背景在前，要处理的材料在最后）。

**对写作的影响**：

- 位置本身是好事，指令紧贴生成点，近因效应最强
- 真正的影响只有一条：**超长技能会把前文推远**，可能稀释更早的上下文
- 不会重复加载：目录的结尾句会告诉模型遵循注入块，不要再用工具重新加载

**实践结论**：不需要为"靠后"做特殊排版，**控制长度就够了**。这条的实际影响比其余几条都小。

## 六、资源基底与相对路径

技能正文加载时，宿主会附带一段**资源指引**，有三种形态：

| 形态 | 指引内容 |
|---|---|
| 目录型 | `Base directory for this skill: <路径>` |
| URL 型 | `Base URL for this skill: <url>` |
| 不透明型 | `Resources for this skill: <一句描述>` |

**因为技能可能来自远程或插件内嵌，资源基底不保证是本地目录。**

**要求**：技能正文引用自己的 `scripts/`、`references/`、`assets/` 时，**用相对路径**，让模型按宿主给出的基底解析。

**反例**：把 `C:\...\skills\my-skill\scripts\run.py` 这样的绝对路径写进正文。在本地来源下能用，一旦技能来自远程或另一台机器就必然失效。

**正确写法**：说明"本技能的脚本位于 `scripts/` 目录"，并指明"按宿主提供的技能基底解析相对路径"。

## 七、对 skill 写作的净影响

汇总成一份可执行清单：

| # | 该做什么 | 依据 |
|---|---|---|
| 1 | 描述要一次想清楚，别在生产会话里反复改 | 目录变更是全量替换 |
| 2 | 描述控制在 500 字符内，重要的放前面 | 目录截断 |
| 3 | 正文引用自己的资源用**相对路径** | 资源基底可为 URL 或不透明 |
| 4 | 正文要短，理由主要是上下文占用，不是费用 | 缓存命中计价，真实代价是窗口占用 |
| 5 | 改了正文后，别指望进行中的会话立即生效 | 正文不做版本化 |
| 6 | 关键约束不能只靠正文长期在场 | 压缩会裁掉工具结果 |
| 7 | 用 `disable-model-invocation` 前想清楚代价 | 模型将完全看不到该技能 |
| 8 | 别指望模型主动提示用户去用 `/name` | 全用户专属时目录整体省略 |
| 9 | 模型提到不存在的技能时，先查来源故障 | 快照不完整保留上一份视图 |
| 10 | 调用策略两个字段默认都是允许，不要乱设 | 省略即允许 |
